# Releasing zmime

The [Release workflow](../.github/workflows/release.yml) prepares a version on the default branch, calls the complete [CI workflow](../.github/workflows/ci.yml) for that exact commit, publishes the crate, and then creates its Git tag and GitHub Release. All stages run in the same workflow execution. GitHub documents which events can be generated by `GITHUB_TOKEN` in its [workflow event reference](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows); this release sequence uses a direct reusable-workflow call for validation.

## Repository setup

Create the repository Actions secret **`CARGO_REGISTRY_TOKEN`** with a crates.io token authorized to publish `zmime`. The workflow gives that secret only to the `cargo publish` step. It never passes the token as a command-line argument, writes it to source files, or supplies it to test jobs. Cargo supports this environment variable for publication; see [cargo publish](https://doc.rust-lang.org/cargo/commands/cargo-publish.html).

The repository's rules must permit the workflow to push its version commit to the default branch and create release tags. The prepare and publish jobs request `contents: write`; validation receives `contents: read` and no registry secret. A protected-branch rejection stops preparation before publication. Keep the workflow on the default branch and run it from that branch.

## Start a release

Open **Actions → Release → Run workflow**, choose the repository's default branch, and select a bump mode. The first release of the checked-in `0.1.0` uses **none**.

| Mode | Example starting at `0.1.0` | Purpose |
| --- | --- | --- |
| `none` | `0.1.0` | Publish the current version or finish an interrupted release |
| `patch` | `0.1.1` | Increment the patch component |
| `minor` | `0.2.0` | Increment minor and reset patch |
| `major` | `1.0.0` | Increment major and reset minor and patch |

For a repository whose default branch is `main`, the equivalent CLI invocation is:

```sh
gh workflow run release.yml --ref main -f bump=patch
```

Preparation checks the trigger, the selected branch, and the current remote branch head. A dispatch whose source has already been overtaken by another commit stops with a fresh-run instruction. A bump edits the explicit package version and the `zmime` path-package entries in both lockfiles, commits those changes, and pushes without force. The resulting version commit can remain on the default branch if later validation fails; `none` is available to publish that version after the failure is resolved.

## Validation and publication order

Every release validates the prepared commit with OS and MSRV tests, portable and SIMD tests, differential tests, cross-target checks, Miri, formatting, clippy, documentation, package-boundary checks, `cargo package`, and `cargo publish --dry-run`. The published crate stays independent of comparison dependencies. The complete executable job definitions are in [ci.yml](../.github/workflows/ci.yml).

The publish job checks that its checkout is the validated SHA, that its manifest matches the prepared version, and that the commit remains reachable from the default branch. It refuses an existing version tag that identifies another commit or an object that is not a commit. It then packages the source and checks the crates.io sparse index before deciding whether to upload.

An existing registry version is reusable only when its SHA-256 matches the newly packaged archive exactly and the version is not yanked. Cargo's [registry index format](https://doc.rust-lang.org/cargo/reference/registry-index.html) supplies the immutable archive checksum used for this decision. A registry error other than a missing entry stops the release; an unavailable registry is never interpreted as proof that a version is free.

After publication, the helper waits for the matching registry entry before creating the annotated `vVERSION` tag. It then creates the GitHub Release, or completes an existing draft for the same verified tag. An already completed compatible release is left intact. Tag creation and crates.io publication are separate remote operations, so failures are handled by resuming the verified state rather than by deleting published content. The implementation is in [release.py](../scripts/release.py).

## Recovery

The workflow serializes release executions and preserves a run identifier in each automatic version commit. Re-running the same Actions run recognizes its own prepared commit at the branch head and reuses the version, including when the original input requested a bump. A newly dispatched recovery run should use **none** when the checked-in version is still the intended release.

Use **Re-run failed jobs** to finish a publication already accepted by crates.io. That preserves the prepared commit and successful validation outputs even if the default branch has subsequently advanced. A fresh `none` run is appropriate when the branch still points to the intended published commit; changed source produces a different archive and is rejected by the checksum check.

| Observed failure | Recovery |
| --- | --- |
| The default branch advanced before preparation | Dispatch a fresh run from the current default branch |
| The version commit was pushed, then a test failed | Fix the test or implementation, keep the intended unpublished version, and dispatch `none` |
| Branch protection rejected the version push | Configure the required repository permission or merge the desired version through the normal protected-branch process, then dispatch `none` |
| `cargo publish` failed before upload | Correct the reported registry/token failure and rerun; no tag or Release is created by the failed upload step |
| Upload succeeded but registry propagation or a network request failed | Re-run failed jobs from the original execution; use a fresh `none` run only while the branch still points to the intended published commit |
| The crate exists but its archive differs | Inspect the existing published artifact and use a new version for different package bytes; the workflow refuses to overwrite or silently reuse it |
| The version is yanked | Select and publish a new version |
| The version tag identifies different source or a non-commit object | Select a new version or resolve the conflicting repository metadata separately; the workflow never force-updates the tag |
| The crate and tag exist but GitHub Release creation failed | Rerun; the registry and tag are verified again before completing the Release |

The archive comparison includes Cargo-generated package metadata. Reproducing an existing archive therefore requires the same source and compatible packaging behavior; a changed archive is reported explicitly even when the apparent Rust source changes are small.

## Verification and completion

The release helper has offline regression tests using temporary Git remotes and simulated registry/Release responses. They cover all bump modes, same-run retries, stale dispatches, wrong branches/events, conflicting and non-commit tags, mismatched lockfiles, exact archive reuse, checksum conflicts, yanked versions, publication visibility, and Release completion. Run them without credentials:

```sh
python3 -B -m unittest discover -s scripts -p 'test_*.py' -v
python3 scripts/check_contract.py
```

A completed release has three matching outcomes: the intended crates.io version, its tag at the validated commit, and a published GitHub Release for that tag. The Actions run records the actual hosted gate results and publication outcome. Local unit-test or workflow-lint results describe their respective checks; deployment status comes from the completed release execution.
